# 按设计稿实现 UI

在研发代码仓库中使用本 Skill。用户要求“按设计稿做页面”时，目标是直接完成符合设计的代码，而非先生成问题清单再等待修复；用户仅要求检查时，保持产品代码只读。工具仓库的 [README](../../../README.md) 和 [接入规范](../../../docs/接入与快照规范.md) 说明采集、配置和报告格式。创建新文件前读取工具仓库《问题与报错日志.md》。

## 动代码前确定实现依据

- 定位准确的 Figma 画板、节点、版本和目标页面状态。读取对应页面的 Comment、Annotation、Measurement；分别记录已读、为空或无法读取，不能把“未获取”当“无要求”。评论可能规定单位、动态内容或例外。必要的测量标注可用 Figma 工具或界面补足。
- 阅读研发仓库中现有页面、组件、设计 token、字体、图片和图标资源、布局方案及目标平台约定。确定哪些可以复用、哪些需要修改，避免在共享组件上引入影响其他页面的全局样式。
- 把设计转成可执行的组件约束：父子结构、Auto Layout/约束与对齐、宽高和内外间距、字体家族/字重/字号/行高、颜色、圆角、边框、素材、文案性质、可见状态，以及目标视口和响应式规则。按 [文案分类](COPY-CLASSIFICATION.md) 区分固定与动态内容。设计未说明的断点或交互行为按项目既有约定处理，并说明关键假设；影响实现的歧义再向用户确认。
- 明确设计单位、CSS px 或 dp/pt、设备截图像素的换算依据；不要固定 720/@2x 或按设备名猜倍率。优先从布局关系和项目 token 实现，而非为单张截图堆绝对定位或事后平移补丁。

## 直接落地设计

- 以设计的组件层级组织代码，使用项目现有框架和可复用组件。先确定容器布局和字体/素材，再实现子元素、状态与交互；图片、图标和字体用可核实的设计资源，不用外观相近的占位物冒充最终实现。
- 对照设计约束填写样式和内容：父容器尺寸、约束和间距要一致，子元素才能自然落位。处理长文案、数据变化、加载/空/错误状态及适用的移动或桌面宽度；未给设计的状态沿用产品约定，避免声称与设计逐项一致。
- 开发请求本身包含必要的代码修改与本地运行。不要把 `check` 命令或问题汇总表当作主要交付物，也不要要求研发手工给每个元素建映射。稳定 selector / accessibility ID 仅在定位歧义或复验需要时补充。

## 完成后核对

- 运行页面或现有 App 测试环境，在设计对应的视口、状态和平台核对整页结构与重点区域；Web 可直接采集网址，原生优先复用已有 Appium 会话或测试框架快照。截图和结构属性互补，原生树未暴露的字号/颜色等不能猜测为已通过。
- 可用 `scripts/yanfa_review.py check --config <配置路径>` 生成 HTML/JSON/Excel；首次确认 suggested-mappings.json 后复用映射。自动配对与未确认的属性差异保留候选，不拿候选当已证实错误。工具只检查已声明且可观测的属性；图片内容、阴影、遮挡、复杂图形和交互仍需结合运行证据核对。
- 发现残余偏差时，先核实设计与运行条件，再定位研发仓库中的实际组件或样式并直接修正。修正后以 `--previous <上一轮/review.json>` 复验；设计版本、状态或设备环境变化时建立新基线，不自动关闭旧问题。不要以“已有报告”作为实现完成的理由。
- 交付已实现的页面、实际验证范围和仍未解决的问题。需要汇总表时提供 HTML/Excel；JSON 保存机器复验依据。问题写明设计值、实际值、差值、节点、代码位置（已核实才写）与证据。覆盖率只代表声明属性的检查程度，不宣称通用还原度分数；无法运行的目标平台明确列出验证缺口。
