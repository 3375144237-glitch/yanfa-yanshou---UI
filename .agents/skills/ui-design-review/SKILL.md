# 按设计稿实现 UI

在研发代码仓库中使用本 Skill，默认优先考虑原生 App。用户要求“按设计稿做页面”时，目标是直接完成符合设计的代码，而非先生成问题清单再等待修复；用户仅要求检查时，保持产品代码只读。工具仓库的 [README](../../../README.md) 和 [接入规范](../../../docs/接入与快照规范.md) 说明采集、配置和报告格式。创建新文件前读取工具仓库《问题与报错日志.md》。

## 动代码前确定实现依据

- 定位准确的 Figma 画板、节点、版本和目标页面状态。读取对应页面的 Comment、Annotation、Measurement；分别记录已读、为空或无法读取，不能把“未获取”当“无要求”。评论可能规定单位、动态内容或例外。必要的测量标注可用 Figma 工具或界面补足。
- 先确认本次要实现的系统、设备规格和设计变体。iOS、Android、鸿蒙各有单独设计时，分别读取，不用一端画板替代其他端；只有通用画板时，先结合项目既有规范确定系统导航、安全区和字体等差异，影响还原结论的缺失信息再确认。
- 阅读研发仓库中现有页面、组件、设计 token、字体、图片和图标资源、布局方案及目标平台约定。确定哪些可以复用、哪些需要修改，避免在共享组件上引入影响其他页面的全局样式。
- 把设计转成可执行的组件约束：父子结构、对齐和间距、字体与字重/行高、颜色、圆角、素材、文案性质、交互状态和适配范围。原生页面还要明确状态栏、导航栏/手势区、刘海与底部安全区、键盘和系统字体缩放是否由系统或业务容器处理，避免重复添加 inset。按 [文案分类](COPY-CLASSIFICATION.md) 区分固定与动态内容。
- 查清 Figma 单位、iOS point、Android dp、鸿蒙项目使用的逻辑单位、截图物理像素及页面坐标原点之间的关系；不要固定 720/@2x 或按设备名猜倍率。设计未说明的行为按项目既有约定处理，注明关键假设。

## 直接落地设计

- 识别项目实际技术栈（UIKit/SwiftUI、Android View/Compose、ArkUI 或跨端框架），在现有组件和 token 体系中实现；共用业务结构可复用，导航、字体、系统控件与安全区等差异在对应平台处理，不强求三端像素完全相同。
- 以设计的组件层级组织代码，先确定容器约束、系统区域和字体/素材，再实现子元素、状态与交互。优先使用可核实的设计资源，不用外观相近的占位物冒充最终实现，也不为单张截图堆绝对定位或平移补丁。
- 对照设计约束填写样式和内容，处理长文案、系统字号变化、不同屏宽、加载/空/错误状态及键盘弹出后的布局。未给设计的状态沿用产品约定，避免声称与设计逐项一致。
- 开发请求本身包含必要的代码修改与本地运行。不要把 `check` 命令或问题汇总表当作主要交付物，也不要要求研发手工给每个元素建映射。稳定 selector / accessibility ID 仅在定位歧义或复验需要时补充。

## 完成后核对

- 对已实现的平台分别在对应设备规格、系统版本、页面状态和设计变体下核对；有真机时再核对字体渲染和系统区域。不能用 Android 结果证明 iOS 或鸿蒙通过。iOS/Android 可复用已有 Appium 会话；鸿蒙需兼容且已验证的驱动或测试框架快照，当前工具不内置鸿蒙驱动。Web/H5 可直接采集网址。截图和结构属性互补，原生树未暴露的字号/颜色等不能猜测为已通过。
- 可用 `scripts/yanfa_review.py check --config <配置路径>` 生成 HTML/JSON/Excel；首次确认 suggested-mappings.json 后复用映射。自动配对与未确认的属性差异保留候选，不拿候选当已证实错误。工具只检查已声明且可观测的属性；图片内容、阴影、遮挡、复杂图形和交互仍需结合运行证据核对。
- 发现残余偏差时，先核实设计与运行条件，再定位研发仓库中的实际组件或样式并直接修正。修正后以 `--previous <上一轮/review.json>` 复验；设计版本、状态或设备环境变化时建立新基线，不自动关闭旧问题。不要以“已有报告”作为实现完成的理由。
- 交付已实现的页面、实际验证范围和仍未解决的问题。需要汇总表时提供 HTML/Excel；JSON 保存机器复验依据。问题写明设计值、实际值、差值、节点、代码位置（已核实才写）与证据。覆盖率只代表声明属性的检查程度，不宣称通用还原度分数；无法运行的目标平台明确列出验证缺口。
