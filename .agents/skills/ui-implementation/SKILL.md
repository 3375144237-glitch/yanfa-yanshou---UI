# 按设计稿实现 UI

在研发代码仓库中使用本 Skill。新建页面、修改现有布局或新增设计状态时，先完成下列准备，再开始写受影响的 UI 代码。只检查已完成的页面时使用独立验收流程。

## 动代码前确定实现依据

- 定位 Figma 画板、节点、版本和目标页面状态；同时读取结构化属性和设计截图。动代码前读取对应页面的评论、开发注释和测量标注，分别记录已读、为空或无法读取。评论里的单位、动态内容和例外要落实到对应组件；不能把读取失败当“无要求”。项目指定评论读取方式时优先使用；否则使用有权读取该画板评论的工具。
- 先确认本次要实现的系统、设备规格和设计变体。iOS、Android、鸿蒙各有单独设计时，分别读取，不用一端画板替代其他端；只有通用画板时，先结合项目既有规范确定系统导航、安全区和字体等差异，影响还原结论的缺失信息再确认。
- 阅读研发仓库中现有页面、组件、设计 token、字体、图片和图标资源、布局方案及目标平台约定。确定哪些可以复用、哪些需要修改，避免在共享组件上引入影响其他页面的全局样式。
- 在动代码前整理一份简短的实现依据：目标端/状态、设计节点 → 代码组件、可复用 token/资源、应保持的尺寸/间距/对齐、字体与字重/行高、颜色/圆角和交互适配规则。原生页面明确状态栏、导航栏/手势区、刘海与底部安全区及键盘由谁处理，避免重复加 inset。按 [文案分类](COPY-CLASSIFICATION.md) 区分固定与动态内容。依据可留在任务上下文，不要求研发手填表或额外建文件。
- 查清 Figma 单位与项目代码单位的对应关系：iOS point、Android dp/sp、鸿蒙项目的 vp/fp 等、Web CSS px，以及各端像素倍率和页面坐标原点。不要固定 720/@2x 或按设备名猜倍率。设计没有规定的适配行为可沿用项目既有约定，注明关键假设。
- 有证据的设计值按依据实现。设计读不到，或关键尺寸、单位、资源和目标状态存在冲突时，暂停受影响的部分并明确缺口，继续做有可靠依据的部分。不要凭单张截图编造精确数值、字体或缺失变体；也不要为了先做出页面而用相似资源替代最终资源。

## 直接落地设计

- 识别项目实际技术栈（UIKit/SwiftUI、Android View/Compose、ArkUI 或跨端框架），在现有组件和 token 体系中实现；共用业务结构可复用，导航、字体、系统控件与安全区等差异在对应平台处理，不强求三端像素完全相同。
- 以设计的组件层级组织代码，先确定容器约束、系统区域和字体/素材，再实现子元素、状态与交互。优先使用可核实的设计资源，不用外观相近的占位物冒充最终实现，也不为单张截图堆绝对定位或平移补丁。
- 对照设计约束填写样式和内容，处理长文案、系统字号变化、不同屏宽、加载/空/错误状态及键盘弹出后的布局。未给设计的状态沿用产品约定，避免声称与设计逐项一致。
- 开发任务交付页面代码和项目正常的构建/运行结果，说明实现的平台、状态和未决设计依据。页面与本轮约定状态可运行后，再按用户或项目流程进入 UI 验收；开发阶段不运行验收采集，不生成问题收集页面。
